# 2단계: 실제 엔진 복제와 macOS 개발 빌드

**상태: 가짜 데이터 전용. 프로덕션 배포 불가.**
2026-09-18, `evaluation/bootstrap` 브랜치의 후속 평가입니다.
수치와 실행 결과는 `stage2-verification.json`, 엔진 정책 결과는 `engine-policy.json`에 기록했습니다.

화면 전체의 시각적 검사, GUI를 통한 금고 생성·수정·복구는 아직 수행하지 않았습니다.

## 체인 시험의 정확한 범위

Autopass 3.3.0, Autobase 7.28.1, Corestore 7.9.2, Hypercore 11.30.2를 실제로 실행했습니다.
동일 Mac에 서로 다른 디스크 저장소 A/B/C를 만들고, 실제 암호화 복제 스트림을 메모리에서 연결했습니다.
저장·복제 엔진은 모의 구현이 아닙니다. 단, 키와 구성원 등록은 테스트 설정으로 제공했습니다.

A-B와 B-C만 허용하고 A-C 직접 스트림은 금지했습니다. C에 없는 A의 변경을 B가 먼저 받은 뒤,
A를 닫고 B도 닫았다가 디스크에서 다시 열었습니다. 그 후 B-C 연결만으로 C가 변경을 받았습니다.
역방향 C-B-A도 C가 닫힌 상태에서 성공했습니다.

**물리 기기 3대, QR 승인, 실제 LAN 발견, NAT 통과, 모바일 백그라운드 동기화 시험은 아닙니다.**

## 출시 전에 보강해야 할 정책

### 작성 권한 회수와 읽기 권한 회수는 다릅니다

기본 엔진에서 B를 `removeWriter()`로 제거하자 `B.writable`은 false가 되었습니다.
그러나 A의 기본 암호화 키는 바뀌지 않았고 B는 제거 이후 생성한 새 가짜 데이터를 읽었습니다.
`eval:policy`는 이를 성공으로 처리하지 않고 종료 코드 2를 반환합니다.

이 결과는 `removeWriter()` 단독으로 우리의 기기 퇴출 요건을 충족할 수 없다는 뜻입니다.
이 API는 작성자 제거 API이므로, 그 자체를 결함이라고 단정하거나 PearPass 앱 전체의 취약점으로 확대하지 않습니다.
앱 수준의 별도 재키잉 흐름은 아직 검증하지 않았습니다. 새 epoch, 새 금고 키, 남은 기기에만 키 전달,
오프라인 구세대 변경의 수용 기준을 포함한 상위 정책이 필요합니다.

### 동시 수정은 수렴하지만 충돌 버전을 별도로 보여줘야 합니다

연결을 끊은 A와 B가 같은 키를 각각 수정한 뒤 다시 연결하면 현재 값은 하나로 수렴했습니다.
기본 `get()` 결과는 한 버전만 보여줍니다. 원시 변경 이력이 삭제되었다는 의미는 아니며,
앱이 다른 경로로 충돌·이력을 표시하는지는 아직 시험하지 않았습니다.
자동완성이 임의의 승자 값을 사용하지 않도록 명시적인 버전 보존·선택 정책을 검증해야 합니다.

## 설치 과정에서 바꾼 점

최초 `npm ci --ignore-scripts`에서는 Git 의존성의 `prepare` 실행이 관찰되어 중단했습니다.
따라서 이 옵션만으로 Git 준비 스크립트를 차단했다고 주장하지 않습니다.
`git-lifecycle-review.json`에는 고정 커밋의 스크립트 목록을 기록했습니다.

대체 설치는 Git 커밋의 소스 압축본과 SHA-512 영수증을 사용하고, 원래 `package.json`의 의존성 선언과
`package-lock.json`을 고치지 않은 채 `.evaluation-install`에서 파생 manifest와 설치 영수증을 만듭니다.
설치가 끝난 패키지는 빌드 도구 호환성을 위해 프로젝트의 일반 `node_modules` 디렉터리에 둡니다.
이 대체 설치 로그에는 준비·설치 훅 실행 헤더가 나타나지 않았습니다. Electron 바이너리 설치는 소스를 확인한 뒤 명시적으로 실행했습니다.
압축본 영수증은 해당 다운로드의 해시 기록이지, 독립된 공급자 서명 검증이나 보안 감사가 아닙니다.

UI의 모바일 전용 타입에 필요한 react-native 0.79.5, react-native-svg 15.11.2,
react-native-reanimated 3.17.5와 그 의존성은 UI 저장소 자체 lockfile에서 추출했습니다.
이는 빌드 도구용 별도 트리이며 앱의 런타임 의존성을 최신 버전으로 일괄 교체한 것이 아닙니다.
전역 Node, npm 설정, 운영 중인 금고를 변경하는 설치 방식은 사용하지 않았습니다.

## 현재 작업 폴더에서 재실행

```sh
cd ~/Developer/pearpass-evaluation-20260918/pearpass-app-desktop
export PATH="$PWD/../.tools/node-v22.23.2-darwin-arm64/bin:$PATH"
npm run eval:test
npm run eval:engine
npm run eval:policy
```

마지막 명령의 종료 코드 2는 현재 관찰된 기밀성 퇴출 요건 실패를 뜻합니다. 실패를 숨기지 마세요.
앱을 열 때는 `npm run dev:eval`을 사용하고 가짜 데이터만 입력합니다.

새 평가 복사본에서 의존성이 없는 경우, 위 Node 선택 후 아래 순서를 사용합니다.
기존 설치가 있으면 설치 도구는 덮어쓰지 않고 중단합니다.

```sh
npm run eval:install-pinned
npm run eval:prepare-ui
electron_config_cache="$PWD/../.tools/electron-cache" node node_modules/electron/install.js
npm run build
```

원본 lockfile 그대로의 일반 `npm ci` 재현에 성공했다고 주장하지 않습니다. 고정 소스 기반의 별도 평가 설치입니다.
`.evaluation-install`과 `.evaluation-reports`는 Git에 올리지 않습니다. 의존성 영수증과 선별한 검증 기록만 공개합니다.

## 다음 개발 게이트

현재 증거는 기존 복제 엔진을 유지하며 평가를 계속할 근거입니다. 코어 전체 재작성은 아직 결정하지 않습니다.
다음 핵심 게이트는 앱의 퇴출 호출 경로 확인, epoch·키 교체 명세와 테스트,
동시 수정 버전 보존 정책, 외부 통신이 차단된 새 설치의 QR/LAN 페어링입니다.
별도 키 교체·충돌 정책을 넣기 전 실제 비밀번호·API 토큰을 사용하거나 배포하지 않습니다.

## 전체 테스트와 스냅샷 검토

최초 push는 기본 Node 19로 실행된 기존 pre-push 훅에서 실패했습니다. 훅을 끄거나 우회하지 않았습니다.
Node 22로 다시 실행하자 `File` 전역 관련 실패는 사라지고 기존 테마 스냅샷 11개 차이만 남았습니다.
실패 차이는 전부 ThemeProvider의 생성 클래스 두 개였으며, 고정 UI 소스의 CSS metadata로 해당 식별자를 확인했습니다.
스냅샷 파일 6개의 해당 클래스 쌍 11곳만 수정했습니다. DOM 구조·텍스트·동작 assertion은 바꾸지 않았습니다.
전체 일괄 `-u`나 테스트 제외로 실패를 숨기지 않았습니다. 이전 생성 식별자가 달라진 정확한 원인은 확정하지 않았으며,
독립적인 시각 검증은 미실행입니다. 검토 기록은 `snapshot-review.json`과 `theme-css-metadata.json`입니다.
최종 Node 22 검사에서 108개 스위트·722개 테스트·13개 스냅샷이 통과했습니다.
커밋과 push 때도 위 프로젝트 Node 경로를 선택해야 사용자 기본 Node 19로 훅이 실행되지 않습니다.
